# Chapter 3 — Optimizing Fonts and Images

## 一、本章学习目标

学完本章，你不应该只记住 `next/font` 和 `next/image` 的 API，而应该理解它们背后的性能问题，以及框架为什么采用这些设计。

- **字体优化**：理解字体加载、fallback font、布局偏移之间的关系，掌握 `next/font` 的基本使用。
- **图片优化**：理解图片尺寸、资源传输、加载时机与布局稳定性的关系，掌握 `next/image` 的基本使用。
- **响应式展示**：区分 CSS 对元素的显示控制与图片资源选择。
- **工程判断**：能够判断某种优化解决了什么问题，以及它的能力边界在哪里。

---

## 二、先建立整体认知：性能优化到底在优化什么？

网站展示一段文本或一张图片，看起来只是简单的 UI 渲染，但浏览器需要完成一系列工作：获取资源、解析相关信息、确定元素尺寸、计算布局，并最终把内容显示到屏幕上。

**字体和图片都可能影响这个过程，但原因并不完全相同**。

**问题一：布局稳定性**

- 资源加载后，元素的尺寸或位置发生变化，导致页面内容移动。

- 典型**原因**：字体切换导致文本尺寸变化；图片没有提前确定宽高比。


**问题二：资源传输成本**

- 浏览器需要下载字体和图片。资源越大、请求链路越复杂，越可能增加加载时间。

- 典型优化：字体自托管、适当的字体子集、按需选择图片尺寸和格式。


**问题三：资源加载时机**

- 页面中的资源并不都同样重要。首屏关键资源和暂时不可见的图片，可以采用不同的加载策略。

- 典型优化：合理的字体预加载、非首屏图片懒加载。


这三个问题需要分别理解：

- **布局稳定性**关注页面是否在加载过程中发生意外移动。
- **资源传输成本**关注下载什么资源、下载多少数据，以及从哪里下载。
- **加载时机**关注资源何时开始加载。

它们可能相互影响，但不是同一个问题。例如，图片懒加载可以减少初始阶段不必要的资源加载，却不能单独解决图片没有预留布局空间的问题。

## 三、Web 基础：Layout Shift 与 CLS

### 3.1 什么是 Layout Shift？

**累积布局偏移（[Cumulative Layout Shift, CLS](https://vercel.com/blog/how-core-web-vitals-affect-seo)）** 是 Google 用于评估网页性能与用户体验的一项核心指标。

Layout Shift（布局偏移）指页面中可见元素的位置发生了意外变化。

对于字体而言，当浏览器最初使用系统默认或回退字体渲染文本，随后在自定义字体加载完成时将其替换，就会发生布局偏移。这种字体替换会导致文本尺寸、行高或字间距发生变动，进而引起周围元素跳动移位。

![image-20261029123428261](./03-优化字体和图片.assets/image-20261029123428261.png)

关键因果链是：

1. 浏览器先使用可用字体绘制文本。
2. 自定义字体加载完成，并被应用到文本。
3. 新字体的字形宽度、字体度量等可能与原字体不同。
4. 文本占据的空间发生变化，可能导致换行或元素尺寸变化。
5. 后续元素的位置随布局重新计算而变化。

**重要区别**：浏览器重新计算布局不一定会产生 CLS。只有符合布局偏移指标判定条件的意外可见位置变化，才会被计入相关指标。

---

### 3.2 CLS 衡量什么？

**Cumulative Layout Shift（CLS，累积布局偏移）**是 Core Web Vitals 中用于衡量页面视觉稳定性的指标。

它关注页面加载和使用过程中出现的意外布局偏移，而不是简单统计发生了多少次重排或重绘。

需要记住：

- 字体加载和图片尺寸未知是常见的布局偏移诱因。
- 有意触发的交互式布局变化与意外布局偏移不能直接等同。
- CLS 不衡量页面的所有性能问题；例如，下载资源耗时较长不一定会产生布局偏移。

因此，字体和图片优化既涉及视觉稳定性，也涉及加载速度，但两者的评价维度不能混为一谈。

## 四、字体优化：`next/font`

### 4.1 为什么要优化字体？

自定义字体能够统一品牌风格、改善视觉设计，但它也引入了额外的资源加载过程。

**如果字体文件尚未加载完成，浏览器可能先使用 fallback font（回退字体），随后切换到自定义字体**。字体之间的度量差异可能引起文本宽度、换行和页面布局变化。

传统方案还可能依赖第三方字体服务，使浏览器需要与额外的域名建立连接并获取字体资源。

当你使用 `next/font` 模块时，Next.js 会自动优化应用中的字体。

Next.js 的 `next/font` 主要希望改善两方面：

1. **字体资源管理**：在构建过程（Build time）中下载字体文件并处理字体资源，并将其与其它静态资源一同托管在本地服务器上。这意味着用户访问页面时，无需向外部第三方服务器发起额外的字体网络请求，从而杜绝由此引发的性能瓶颈。
2. **字体加载与视觉稳定性**：提供字体预加载和 fallback 字体相关优化能力，降低加载过程中出现布局变化的风险。

这里的关键不是“让浏览器不再加载字体”，而是让字体资源的获取与交付方式更可控。

---

### 4.2 `next/font` 的基本工作过程

以本章使用的 Google Font `Inter` 为例，可以把过程理解为：

![image-20261029123903600](./03-优化字体和图片.assets/image-20261029123903600.png)

课程中“构建时下载、与静态资源一起托管”的说法，主要描述的是字体资源的获取与部署方式。

**它不代表字体数据已经被直接嵌入 HTML，也不代表浏览器完全不需要网络请求**。

浏览器仍可能需要请求应用自身提供的字体文件。

减少的是对外部字体服务的运行时依赖及其相应请求链路。

### 4.3 添加主字体（课程实践）

让我们向应用中引入一个 Google 字体，观察其实际效果。

在 `/app/ui` 目录下新建一个名为 `fonts.ts` 的文件，该文件用于集中管理应用中所需的全局字体配置。方便整个应用复用。

从 `next/font/google` 模块导入 `Inter` 字体（作为主字体），并指定要加载的字符子集（subset），此处设置为 `'latin'`：

```ts
// app/ui/fonts.ts
import { Inter } from 'next/font/google';

export const inter = Inter({
  subsets: ['latin'],
});
```

逐项理解：

| 代码                 | 含义                                                 |
| -------------------- | ---------------------------------------------------- |
| `Inter`              | 由 `next/font/google` 提供的字体配置函数             |
| `subsets: ['latin']` | 指定需要包含的字符子集，避免不必要地引入其他字符集合 |
| `inter`              | 导出的字体配置对象，供其他模块复用                   |
| `inter.className`    | 由字体配置生成、用于应用字体样式的类名               |

为什么把字体放到独立文件？

这不是 Next.js 强制要求的目录结构，而是一种组织方式。字体配置可以在多个页面和组件之间共享，避免每个组件都重复声明字体。

---

### 4.4 在根布局中应用字体（课程实践）

随后，将该字体应用到 `/app/layout.tsx` 中的 `<body>` 元素上：

```tsx
// app/layout.tsx
import '@/app/ui/global.css';
import { inter } from '@/app/ui/fonts';

export default function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <html lang="en">
      <body className={`${inter.className} antialiased`}>
        {children}
      </body>
    </html>
  );
}
```

这里最重要的是：

```tsx
<body className={`${inter.className} antialiased`}>
```

- `inter.className`：将 `inter.className` 添加到 `<body>` 标签后，该字体将**全局生效**。普通情况下，后代元素可以继承相应的 `font-family`，除非其他样式覆盖它。
- `antialiased`：课程使用的 Tailwind CSS 类，用于调整字体抗锯齿相关的渲染方式。它不是加载字体所必需的配置，也不能代替字体优化。

为什么放在根布局？

因为根布局通常包裹应用的主要页面。把字体应用在这里，可以让整个应用默认使用统一字体，而不是每个页面分别设置。

### 4.5 练习：添加辅助字体

你也可以将字体指定给局部的特定元素。

现在轮到你动手了：在 `fonts.ts` 文件中导入辅助字体 `Lusitana`，并将其应用到 `/app/page.tsx` 文件的 `<p>` 元素上。

除了指定字符子集外，你还需要配置字重（font weight），例如 `400`（常规）和 `700`（加粗）。

```ts
// app/ui/fonts.ts
import { Inter, Lusitana } from 'next/font/google';

export const inter = Inter({
  subsets: ['latin'],
});

export const lusitana = Lusitana({
  subsets: ['latin'],
  weight: ['400', '700'],
});
```

有时应用需要不同字体来区分标题、品牌 Logo 或正文。

> **操作提示：**
>
> - 如果不确定字重参数的传递格式，可查看代码编辑器中的 TypeScript 类型错误提示。
> - 访问 Google Fonts 官网搜索 Lusitana 查看其支持的字重规格。
> - 查阅官方文档了解多字体配置及完整参数项。

在页面中：

```tsx
import AcmeLogo from '@/app/ui/acme-logo';
import { ArrowRightIcon } from '@heroicons/react/24/outline';
import Link from 'next/link';
import { lusitana } from '@/app/ui/fonts';
 
export default function Page() {
  return (
    // ...
    <p
      className={`${lusitana.className} text-xl text-gray-800 md:text-3xl md:leading-normal`}
    >
      <strong>Welcome to Acme.</strong> This is the example for the{' '}
      <a href="https://nextjs.org/learn/" className="text-blue-500">
        Next.js Learn Course
      </a>
      , brought to you by Vercel.
    </p>
    // ...
  );
}
```

此时，该段文本使用 Lusitana，而应用其余部分仍可默认使用 Inter。

**理解重点**：字体配置定义了字体资源和样式，`className` 负责把对应样式应用到元素。这两个步骤分别解决“字体如何配置”和“字体应用在哪里”的问题。

---

### 4.6 字体子集、字重与字体预加载

这三个概念容易混淆。

| 配置或机制        | 主要作用                               | 不代表什么                         |
| ----------------- | -------------------------------------- | ---------------------------------- |
| `subsets`         | 指定需要的字符集合                     | 不等于设置显示语言                 |
| `weight`          | 指定需要的字重                         | 不等于设置文字大小                 |
| `className`       | 应用生成的字体样式                     | 不等于下载字体的全部过程           |
| `preload`         | 在适用情况下提前发现并加载关键字体资源 | 不保证字体永远不会造成布局偏移     |
| fallback 字体调整 | 尽量减少备用字体与最终字体的度量差异   | 不保证所有文字都具有完全一致的布局 |

课程没有要求手动配置 `preload`，因此本章只需理解其作用，不必额外引入配置。

---

### 4.7 `Inter_Fallback` 是什么？

课程让你在开发者工具中查看 `body` 的样式，可能会看到 `Inter` 和 `Inter_Fallback`。

它们不代表页面同时把两个普通字体都应用为最终字体。

可以从 CSS 字体栈理解这一现象：浏览器会按照字体声明及其回退规则选择实际用于绘制文本的字体。Next.js 还可以为字体生成回退相关的样式，以缓解字体加载前后的度量差异。

要注意：`Inter_Fallback` 是观察生成样式时可能遇到的名称，不应把它理解成一个需要手动导入的标准字体 API。

本节核心结论：`next/font` 不只是一个导入字体的便捷接口，它还管理字体资源和相关 CSS，帮助应用减少外部字体依赖，并改善字体加载体验。

## 五、图片优化：`next/image`

### 5.1 为什么普通的 `<img>` 还不够？

Next.js 可以托管根目录下 `/public` 文件夹内的静态资源（如图片），这些资源可以在应用代码中直接引用。

如果使用传统原生 HTML，添加图片的方式如下：

```html
<img
  src="/hero.png"
  alt="Screenshots of the dashboard project showing desktop version"
/>
```

这段代码本身完全合法，也可能工作得很好。

但这意味着你必须手动解决以下工程问题：

- 确保图片在不同屏幕尺寸下具备自适应响应能力。
- 针对不同终端设备提供对应尺寸规格的图片源。
- 避免图片加载过程中造成的布局偏移（CLS）。
- 对处于视口（Viewport）之外的图片执行懒加载。

图片优化是 Web 前端性能工程的重要领域。`next/image` 组件内置了自动化处理流程，免去了手动配置这些特性的成本。

---

### 5.2 `Image` 的核心职责

```tsx
import Image from 'next/image';

<Image
  src="/hero.png"
  width={1000}
  height={760}
  alt="Dashboard preview"
/>
```

`<Image>` 组件是原生 HTML `<img>` 标签的增强扩展版，内置以下优化机制：

- **自动消除布局偏移**：加载时自动预留占位区域，避免页面抖动。
- **按需调整尺寸**：避免向下级或小屏设备发送高分辨率超大文件。
- **默认开启懒加载**：仅当图片滚动至视口边缘时才按需发起请求。
- **现代格式支持**：当客户端浏览器支持时，优先输出 WebP 或 AVIF 格式。

这些能力有各自的条件和边界，不能理解为每次渲染都会自动执行所有优化。

---

### 5.3 添加桌面端主视觉图

查看 `/public` 目录，可以看到两个文件：`hero-desktop.png` 和 `hero-mobile.png`。它们的构图各不相同，分别用于桌面端与移动端展示。

在 `/app/page.tsx` 中导入 `next/image`，并在相应注释下方写入组件：

```ts
// /app/page.tsx
import AcmeLogo from '@/app/ui/acme-logo';
import { ArrowRightIcon } from '@heroicons/react/24/outline';
import Link from 'next/link';
import { lusitana } from '@/app/ui/fonts';
import Image from 'next/image';

export default function Page() {
  return (
    // ...
    <div className="flex items-center justify-center p-6 md:w-3/5 md:px-28 md:py-12">
      {/* 在此添加主视觉图 */}
      <Image
        src="/hero-desktop.png"
        width={1000}
        height={760}
        className="hidden md:block"
        alt="Screenshots of the dashboard project showing desktop version"
      />
    </div>
    // ...
  );
}
```

此处将 `width` 设置为 `1000`，`height` 设置为 `760`。

显式声明宽高是一项防止布局偏移的最佳实践。

**这两个数值必须严格对应原图的宽高比例**。

需要注意，它们的作用是让浏览器推断**固有宽高比**以便提前保留渲染占位，而不是限制页面上的最终物理展示尺寸。

代码中配合使用了 Tailwind 类名：`hidden` 在移动端将图片隐藏，`md:block` 则在桌面端恢复显示。

---

### 5.4 图片的 `width` 和 `height` 为什么重要？

这是本章最需要真正理解的知识点之一。

假设图片的固有尺寸为 $1000 \times 760$，那么它的宽高比为：

$$
\frac{1000}{760}\approx 1.316
$$

**当浏览器提前知道图片的宽高比时，就能根据布局中可用的宽度推算相应高度，从而为图片预留空间**。

例如，显示宽度为 $500$ CSS 像素，并且保持原始比例：

$$
h=500\times\frac{760}{1000}=380
$$

因此，浏览器可以预留大约 $500 \times 380$ CSS 像素的空间。

这有助于避免图片加载后才突然撑开容器，推动后续元素下移。

但要区分两件事：

- `width={1000}`、`height={760}`：向 Next.js 和浏览器提供图片的尺寸信息，用于确定比例等信息。
- CSS 布局规则：**决定图片最终如何在页面中显示**。

例如：

```tsx
<Image
  src="/hero.png"
  width={1000}
  height={760}
  alt="Dashboard preview"
  className="w-full h-auto"
/>
```

**这里的 CSS 让图片宽度适应容器，并保持自动计算的高度**。图片最终不必显示为 $1000 \times 760$ CSS 像素。

边界：提供宽高信息有助于减少布局偏移，但并不保证整个页面没有 CLS。容器尺寸变化、CSS 覆盖、其他内容插入等情况仍可能造成布局变化。

---

### 5.5 图片尺寸调整、懒加载与现代格式

这三种机制针对不同的问题。

#### 1. 尺寸调整：减少不必要的图像数据

如果原图尺寸很大，而设备只需要显示较小的图片，就可以根据需求提供更合适的尺寸变体。实际输出取决于源图片、配置和优化器支持。

#### 2. 懒加载：推迟非关键资源加载

当图片尚未接近视口时，可以推迟加载。`next/image` 默认对适用的普通图片使用懒加载策略。对关键首屏图片，应根据实际情况决定是否需要优先加载。

#### 3. 现代格式：降低传输成本

WebP 和 AVIF 等格式在适当的画质和编码参数下，通常能比传统格式提供更高效的压缩。实际收益取决于图片内容、编码设置及浏览器支持。

这三种机制不能互相替代：

- 尺寸调整解决的是图片分辨率与实际显示需求之间的匹配。
- 懒加载解决的是图片何时开始加载。
- 格式选择解决的是图片如何编码、传输多少数据。

例如，把一张 4000 像素宽的图片改成懒加载，不代表它下载时会自动变成适合手机的尺寸；而把图片转成 WebP，也不代表它已经具备正确的布局尺寸。

### 5.7 `srcset` 和 `sizes` 的基本作用

响应式图片还涉及两个常见 HTML 概念。

- `srcset`：提供不同候选图片资源。
- `sizes`：描述图片在不同布局条件下预计占据的显示宽度，帮助浏览器选择适合的候选资源。

例如，同一张图片可能有多个尺寸变体。浏览器可以结合视口、显示尺寸和设备像素密度，选择更合适的资源。

Next.js 的 `Image` 可以根据配置生成相应的响应式图片标记；当图片需要随布局宽度变化时，合理的 `sizes` 配置很重要。

本章的桌面与移动端 Hero Image 示例采用的是两张不同图片 + CSS 控制显示，不是完整的 `srcset`/`sizes` 方案。两种做法都与响应式图片有关，但解决问题的方式不同。

## 六、常见误区与边界条件

| 常见说法                                          | 更准确的理解                                                 |
| ------------------------------------------------- | ------------------------------------------------------------ |
| 使用 `next/font` 后，浏览器就不需要请求字体文件。 | 字体由应用自托管，但浏览器仍可能请求字体资源。               |
| 只要设置图片宽高，页面就绝不会发生 CLS。          | 宽高信息帮助预留空间，但不能消除所有布局偏移。               |
| `width` 和 `height` 决定图片最终的 CSS 显示尺寸。 | 它们提供尺寸信息，最终显示大小还受 CSS 和容器布局影响。      |
| 所有图片都会懒加载。                              | 默认懒加载适用于普通图片；优先加载等场景需要区别处理。       |
| `next/image` 总会生成更小的图片。                 | 实际优化结果取决于图片、请求尺寸、配置、优化器和缓存等因素。 |
| 使用现代图片格式就一定更快。                      | 传输收益取决于文件大小、编码质量、解码成本与实际场景。       |
| `hidden` 一定能阻止图片网络请求。                 | CSS 隐藏本身不保证不请求资源。                               |
| 桌面图和手机图是响应式图片的唯一实现方式。        | 也可以使用同一组图片的不同尺寸变体，并通过 `srcset`、`sizes` 等机制选择资源。 |

### 6.1 本地图片与远程图片的区别

课程使用 `public` 目录下的本地图片，因此可以直接使用路径：

```tsx
<Image
  src="/hero-desktop.png"
  width={1000}
  height={760}
  alt="Dashboard preview"
/>
```

对于远程图片，通常需要提供完整的图片 URL，并按照项目所使用的 Next.js 版本和配置要求，允许相应的远程图片来源。

不能把本地图片示例直接当成所有远程图片场景的完整配置指南。

---

### 6.2 不要把框架提供的能力理解为无条件保证

Next.js 提供优化机制，并不意味着开发者不再需要做性能判断。

例如：

- 字体选择仍会影响文本的视觉效果和度量。
- 图片的实际尺寸仍应与布局需求匹配。
- 首屏关键图片与非首屏图片的加载策略可能不同。
- CSS、容器布局和其他动态内容仍可能造成布局偏移。

更准确的理解是：框架提供了更好的默认机制，但开发者仍需要根据页面实际行为验证优化结果。

## 八、自测：用推理验证理解

尝试先独立回答，再展开参考答案。不要只检查自己是否记住了 API 名称。

1. **为什么自定义字体加载完成后，页面可能发生布局偏移？**

   从字体度量、文本换行和后续元素的位置思考。

   > [!tip]
   >
   > 如果字体尚未加载完成，浏览器可能首先会使用 fallback font，等待字体加载完成后，才会使用自定义字体。那么从 fallback font 切换到自定义字体的这个过程就有可能发生布局偏移（layout shift）
   >
   > 自定义字体与 fallback font 的字形宽度和度量可能不同，字体切换后文本尺寸或换行发生变化，导致周围元素重新布局并可能产生意外的可见位置变化。

   

2. **next/font 的自托管是否意味着浏览器不再请求字体文件？**

   区分构建阶段与浏览器运行阶段。

   > [!tip]
   >
   > 不是。构建阶段获取并处理字体资源，部署时由应用提供字体文件；浏览器仍可能需要向应用请求这些资源。

   

3. **图片的 width 和 height 为什么能帮助减少 CLS？**

   想想浏览器在图片下载完成前知道什么。

   > [!tip]
   >
   > 它们提供图片尺寸信息，使浏览器能够推算宽高比并提前预留布局空间，减少图片加载后突然撑开页面的情况。

   

4. **图片懒加载与图片尺寸调整有什么区别？**

   一个关注时间，一个关注什么？

   > [!tip]
   >
   > 懒加载控制何时开始加载资源；尺寸调整控制提供的图像尺寸是否适合显示需求。二者解决不同问题。

5. **为什么 hidden 不一定能阻止图片请求？**

   区分 CSS 的显示控制与浏览器的资源加载。

   > [!tip]
   >
   > hidden 控制元素的显示状态，不是通用的网络请求取消机制。资源是否请求还取决于浏览器的资源发现、加载策略及其他条件。

6. **如果页面仍然发生 CLS，你应该怎么排查？**

   不要直接认定是字体或图片的问题。

   > [!tip]
   >
   > 先观察布局偏移发生的时间和受影响元素，再结合 Performance、Layout Shifts、Network 等开发者工具信息，检查字体切换、图片尺寸、动态插入内容、CSS 布局变化等可能原因。

## 九、本章总结

学完 Chapter 3，应该形成以下认识：

1. 字体优化的核心：管理字体资源与加载行为，减少外部依赖，并降低字体切换造成布局变化的风险。
2. 图片优化的核心：在合适的时间加载合适的图片资源，同时提前确定布局所需的尺寸信息。
3. Next.js 的角色：通过 `next/font` 和 `next/image` 提供更完善的默认机制，减少手动处理资源优化细节的负担。
4. 工程实践的关键：理解 API 背后的机制，并通过实际页面和浏览器开发者工具验证效果，而不是把框架的默认行为当作绝对保证。

完成本章后，你就具备了理解下一章的基础：当页面越来越多时，如何使用 Next.js 的 Layouts 和 Pages 组织应用结构，同时让字体、样式及其他公共 UI 在合适的范围内复用。
